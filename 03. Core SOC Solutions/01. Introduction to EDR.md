# Introduction to EDR

## Task 3 — Beyond the Antivirus

### Why Do We Need EDR if Antivirus Is Already Installed?

Both Antivirus (AV) and Endpoint Detection and Response (EDR) aim to protect endpoints, but they provide different levels and types of visibility, detection, and response.

A traditional AV approach is commonly associated with identifying known malicious files through signatures. If a file has no known signature, a signature-only control may fail to identify it.

EDR extends endpoint protection by continuously collecting and analyzing endpoint activity. It can help identify suspicious behavior even when the original file or payload is not already known.

> **Core distinction:** AV is commonly associated with detecting known malicious files; EDR adds continuous behavioral visibility, investigation context, and response capabilities across endpoints.

### Airport Analogy

TryHackMe compares endpoint protection to airport security:

- **Antivirus — Immigration check:** checks incoming people against a database of known criminals. Someone not previously identified may pass the initial check.
- **EDR — Security officers inside the airport:** monitor activity through cameras and sensors, looking for suspicious behavior after entry. They can investigate, take action, or alert airport management.

The analogy illustrates why checking a file only at the point of arrival is not enough. Monitoring what happens after execution can reveal activity that was not recognizable beforehand.

### Organization-Wide Visibility

EDR can provide visibility across multiple endpoints through a centralized console. For example, when a suspicious file is detected on one endpoint, an analyst can use the EDR platform to investigate whether the same file or related indicators appear on other endpoints.

This helps the SOC understand whether an event is isolated or potentially part of a wider incident.

## Attack Scenario: Phishing to Remote Access

The room presents an attack in which a user opens a malicious Word document and the attacker progresses through several stages.

### Attack Chain

1. **Phishing email:** The user receives an email containing a Word document with a malicious VBA macro.
2. **Document opened:** The user downloads and opens the document.
3. **Macro execution:** The macro executes silently and spawns PowerShell.
4. **Payload download:** The macro runs an obfuscated PowerShell command to download a second-stage payload.
5. **Process injection:** The payload is injected into a legitimate `svchost.exe` process.
6. **Remote access:** The attacker gains remote access to the system.

### AV vs. EDR at Each Stage

| Attack stage | AV response described in the room | EDR response described in the room |
|---|---|---|
| 1. File download | May do nothing if the file has no known signature. | Logs the file download activity and monitors it. |
| 2. Word document opened | May not react because `winword.exe` is a legitimate utility. | Records the execution of `winword.exe` and continues monitoring. |
| 3. Macro spawns PowerShell | May miss the macro if it has no known signature. | Can flag the unusual parent-child relationship between `winword.exe` and `powershell.exe`. |
| 4. Obfuscated PowerShell | May not detect the obfuscated script. | Can flag the suspicious script execution using behavioral and command-line telemetry. |
| 5. Process injection | The room describes traditional AV as potentially missing the injection because it does not monitor memory injection activity in the same way. | Can detect indicators of process injection into `svchost.exe`. |
| 6. Outbound connection | The room describes limited network-level visibility. | Can flag unexpected outbound network behavior associated with `svchost.exe`. |
| Final action | The activity may be marked as clean. | Generates an alert with the attack-chain context and enables analyst response from the EDR console. |

### Important Process Relationship

A key detection opportunity is the unusual process chain:

```text
WINWORD.EXE
    └── powershell.exe
```

Microsoft Word is a legitimate application, and PowerShell is a legitimate administration tool. However, a document application spawning PowerShell can be suspicious and deserves investigation.

**Do not treat this relationship alone as proof of compromise.** The analyst must validate the command line, process ancestry, user context, file activity, network activity, and other available evidence.

### Important Terms

| Term | Meaning |
|---|---|
| Signature-based detection | Detection based on known signatures or indicators associated with threats. |
| Behavioral detection | Detection based on what a process, file, or user does rather than only its identity. |
| Process tree | A representation of process relationships, including parent and child processes. |
| Parent process | The process that starts another process. |
| Child process | A process started by another process. |
| VBA macro | Code embedded in an Office document that can automate actions. |
| Obfuscation | Making code or commands harder to understand or analyze. |
| Process injection | A technique in which code is executed within the address space of another process. |
| `svchost.exe` | A legitimate Windows process used to host services. Its name alone does not establish that activity is benign. |
| C2 (Command and Control) | Infrastructure or communication used by an attacker to control compromised systems. |

## SOC Analyst L1 Investigation Notes

An alert showing `WINWORD.EXE` spawning `powershell.exe` should be investigated, not automatically classified as a confirmed compromise.

### Initial Triage Checklist

1. **Validate the alert**
   - Confirm the hostname, username, timestamp, detection name, and severity.
   - Check whether the activity is expected in the user's role and environment.

2. **Review the process tree**
   - Identify the parent and child processes.
   - Review the full PowerShell command line and execution context.
   - Check whether additional processes were spawned.

3. **Inspect file activity**
   - Identify the document and any files created or downloaded.
   - Record relevant file paths and hashes where available.
   - Check whether the downloaded payload was executed.

4. **Review network activity**
   - Identify outbound connections associated with the relevant processes.
   - Review destination IPs, domains, ports, timestamps, and connection context.
   - Look for evidence of suspicious external communication.

5. **Check for further compromise**
   - Investigate process-injection indicators.
   - Review relevant registry and persistence-related activity.
   - Search other endpoints for the same file, hash, domain, IP, or related indicators.

6. **Determine disposition and escalate**
   - Decide whether the evidence supports a false positive, suspicious activity, or true positive.
   - Preserve relevant evidence and document the investigation.
   - Follow the organization's playbook and escalation process. Do not isolate a host or terminate a process without considering business impact and authorization.

### Evidence Still Needed

The initial process relationship is an investigative lead, not a complete incident conclusion. To establish what happened, the analyst needs corroborating telemetry such as:

- Full process command line and process ancestry.
- File creation, download, and execution records.
- Network connection telemetry.
- Memory or process-injection detections, where available.
- Relevant registry changes and persistence indicators.
- Evidence from other endpoints if the activity may be widespread.

## Key Takeaways

- Traditional signature-based AV may miss previously unknown or sufficiently modified threats.
- EDR adds continuous endpoint telemetry, behavioral detection, investigation context, and response capabilities.
- Process relationships can reveal suspicious activity even when the involved applications are legitimate.
- A suspicious event is not automatically a confirmed incident; context and corroborating evidence matter.
- EDR can support organization-wide investigation by helping analysts search for related activity across endpoints.
- EDR complements other security controls. The room notes that some modern AV products have enhanced visibility and detection, so the comparison is a simplified distinction rather than a claim that every AV product is limited to signatures.

## Quick Revision

- **Why EDR?** To add behavioral visibility, detection, investigation, and response beyond basic known-signature detection.
- **What is the key process clue in this scenario?** `WINWORD.EXE` spawning `powershell.exe`.
- **What happens after PowerShell starts?** The scenario describes an obfuscated command downloading a second-stage payload.
- **What is process injection here?** The payload is injected into a legitimate `svchost.exe` process.
- **What should an L1 analyst do?** Validate the alert, reconstruct the process chain, inspect file and network activity, assess impact, document findings, and escalate according to the playbook.
