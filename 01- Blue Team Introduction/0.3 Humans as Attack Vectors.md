## 1. Definition
**Social Engineering (SE)** is the psychological manipulation of people into performing actions or divulging confidential information. **Phishing** is the most widespread digital delivery mechanism for SE. Goals: harvest credentials, deliver malware, or start fraud such as Business Email Compromise (BEC).

## 2. Why defenders care
- EDR, firewalls, and AV struggle against a user who willingly hands over credentials or approves an MFA prompt.
- With valid credentials the attacker needs no exploit. They just log in.
- To the SIEM and the FortiGate, the activity looks like a normal user working remotely.

## 3. How it works

**Simple:** Attacker sends a fake email ("Urgent: Update Payroll"). User clicks, lands on a fake Microsoft 365 login page, types the password. Attacker gets it.

**Technical (modern threat): AiTM (Adversary-in-the-Middle)**
1. Attacker runs a reverse proxy (e.g. Evilginx) in front of the real login page.
2. User enters password. Proxy forwards it to the real Microsoft/Okta server in real time.
3. User completes MFA. Proxy forwards that too.
4. Real server returns an authenticated **session cookie** (e.g. `ESTSAUTH`, `ESTSAUTHPERSISTENT` for Entra ID).
5. Proxy passes the cookie to the user (login looks normal) and keeps a copy.
6. Attacker replays the cookie. Session is already authenticated, so MFA is bypassed.

> Phishing-resistant MFA (FIDO2/passkeys) breaks this attack because the credential is bound to the real domain.

## 4. Key terms
| Term | Meaning |
|------|---------|
| Credential harvesting | Stealing usernames and passwords |
| AiTM | Intercepting the auth flow to steal session tokens and bypass MFA |
| Session/token replay | Reusing a stolen cookie or token from attacker infrastructure |
| Pretexting | Fabricated scenario (e.g. fake "IT repair" call) to extract info |
| Vishing / Smishing | Voice / SMS phishing |
| Typosquatting | Look-alike domains (e.g. `micr0soft-login.com`) |
| BEC | Fraud via compromised or spoofed business email, often targeting payments |
| MFA fatigue | Spamming push prompts until the user approves |

## 6. Defender view

### Log sources
- Email gateway (Proofpoint, Mimecast, Defender for Office 365)
- Entra ID **SigninLogs**, **AuditLogs**, risk detections
- Exchange / Office 365 audit logs (`OfficeActivity`, Unified Audit Log)
- Proxy / DNS logs (newly registered domains, lookalikes)
- Windows Security `4624` (Logon Type 3/10): relevant for **on-prem/hybrid** logons only, not for cloud AiTM

### Detection signals
- Entra sign-in: success + MFA satisfied, but new IP/ASN/country/device, user-agent mismatch, or high risk level
- Entra ID Protection risk detection: **Attacker in the Middle**, anomalous token, unfamiliar sign-in properties
- Impossible travel
- New inbox rule forwarding/redirecting externally, or rules that delete/move mail
- New MFA method or device registered shortly after a risky sign-in
- New OAuth app consent
- Newly registered domains in email URLs

### Response
1. Revoke all sessions/refresh tokens (kills the stolen cookie). Resetting the password alone is not enough.
2. Reset password; disable account if needed (hybrid: AD disable syncs with delay, so revoke in Entra explicitly).
3. Remove attacker-added MFA methods and registered devices.
4. Review and remove malicious inbox rules, mailbox delegates, and OAuth consents.
5. Search the tenant for the same phishing email; purge it; block sender, domain, URL.
6. Check what the attacker accessed (mail, SharePoint, OneDrive). Scope the incident.
7. Notify Finance/management; freeze suspicious payments.
8. Isolate the host if malware was delivered.

### Prevention
- Phishing-resistant MFA (FIDO2 / passkeys)
- Conditional Access: compliant/managed device, token protection, sign-in risk policies, short session lifetime for sensitive apps
- Block external auto-forwarding in outbound spam policy
- SPF, DKIM, DMARC enforced
- Disable legacy authentication
- "Report phishing" button + simulation + training (support, not blame)

## 7. Mini scenario
- **Attack:** Finance user gets a "DocuSign Invoice" email, hits an AiTM page, enters credentials, approves MFA. Attacker steals the session cookie.
- **Detect:** Alert "Suspicious inbox rule created". Attacker logged into OWA with the stolen session and forwarded all mail containing "invoice" to an external Gmail address.
- **Respond:** Revoke Entra sessions, reset password, remove the rule and any new MFA method, purge the phishing email tenant-wide, alert Finance to hold pending transfers, scope other mailbox access.

## 8. Detection samples

> Table and column names vary by tenant and connector. Verify in your environment.

**Suspicious inbox forwarding rules (Microsoft Sentinel KQL)**
```kusto
OfficeActivity
| where Operation in ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| where Parameters has_any ("ForwardTo", "RedirectTo", "ForwardAsAttachmentTo")
| project TimeGenerated, UserId, Operation, Parameters, ClientIP
```

**Risky successful sign-ins (Entra ID)**
```kusto
SigninLogs
| where ResultType == 0
| where RiskLevelDuringSignIn in ("high", "medium")
| project TimeGenerated, UserPrincipalName, IPAddress, Location,
          AppDisplayName, AuthenticationRequirement,
          RiskLevelDuringSignIn, RiskEventTypes_V2
```

## 9. Free tools
- **urlscan.io / PhishTank:** analyze and screenshot suspicious URLs safely
- **Canarytokens:** honeytokens (fake docs/links) that alert on access
- **GoPhish:** open-source framework for internal awareness campaigns
- **Microsoft Defender / Entra ID Protection reports** (included in some licenses)
- **Sigma + sigmac/pySigma:** convert generic rules to your SIEM format

## 10. Lab idea
- **Safe detection lab (recommended):** Use your own Microsoft 365 test tenant. Generate risky sign-ins (VPN/Tor-like IP, new device), create a test inbox forwarding rule, then find them in `SigninLogs` and `OfficeActivity` with the KQL above.
- **AiTM mechanics (advanced, authorized only):** Run Evilginx against **your own test tenant and your own domain** in an isolated environment. Observe how the cookie is captured, then hunt the replayed session in Entra sign-in logs. Never target accounts or domains you do not own.
- **Awareness campaign:** Run GoPhish internally with written management approval.
- Online: TryHackMe, LetsDefend, and CyberDefenders have phishing-analysis labs.

## 11. Common mistakes
- **MFA fallacy:** Assuming MFA stops phishing. AiTM steals the post-MFA session. Only phishing-resistant MFA and device-bound controls help.
- **Ignoring BEC:** Checking only for malware and missing silent mailbox monitoring and payment fraud.
- **Password reset only:** Not revoking sessions, MFA methods, and rules. Attacker keeps access.
- **Blaming users:** Scolding instead of asking why the gateway delivered the email and why Conditional Access allowed the session.
- **Trusting geo-IP alone:** Attackers use residential proxies near the victim.

## 12. Recap
1. Attackers bypass technical controls by tricking users into granting access.
2. AiTM kits steal post-MFA session cookies, bypassing standard MFA.
3. Phishing (T1566) and stolen credentials rank among the top initial access vectors.
4. Post-compromise often includes hidden forwarding rules for BEC.
5. Defend with layers: phishing-resistant MFA, Conditional Access, email filtering, session revocation playbooks, and user training.
