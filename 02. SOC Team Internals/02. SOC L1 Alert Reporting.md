# SOC L1 Alert Reporting (TryHackMe): Study Notes

## 1. Big Picture
- Triage only decides "threat or not." It stops nothing.
- **Reporting** preserves evidence and gives L2 instant context.
- **Escalation** routes True Positives to people who can remediate.
- **Communication** gets facts logs can't show (IT confirming admin rights, HR confirming a new hire).
- Without all three, a correct verdict can still end in a missed breach.

---

## 2. Alert Funnel

```
SIEM / EDR / ticket platform
        │
        ▼
   L1 (you): triage
        │── most alerts: closed as False Positives or handled at L1
        │
        ▼ (complex / threatening → escalate with report)
   L2: deeper analysis, validates TP, remediates most breaches
        │
        ▼ (major incidents)
   Formal Incident Response / DFIR
```

- **L1 closes:** False Positives and anything fully handled at L1.
- **Goes up:** True Positives needing deeper investigation or remediation, plus alerts you don't fully understand.
- **L3** appears in the room as the next emergency contact after L2.
- [Extra] L3 typically handles advanced investigations and threat hunting. DFIR = Digital Forensics and Incident Response.
- Marking an alert True Positive does **not** stop the attack. Escalation triggers the response.

## 3. Alert Reporting

### Why L1 writes reports (3 purposes from the room)

| Purpose | Explanation |
|---|---|
| Provide context for escalation | Saves L2 time. They understand what happened without starting from scratch |
| Save findings for the records | Raw SIEM logs are kept **3–12 months**. Alerts are kept **indefinitely**. Evidence must live inside the alert |
| Improve investigation skills | "If you can't explain it simply, you don't understand it well enough" |

### The 5Ws

| W | What it covers |
|---|---|
| **Who** | Which user logged in, ran the command, or downloaded the file |
| **What** | The exact action or event sequence |
| **When** | Exact start and end of the suspicious activity |
| **Where** | Which device, IP, or website was involved |
| **Why** | **The most important W.** Your reasoning for the final verdict |

### Bad vs Good: Phishing

**Bad:**
```
Phishing alert. User clicked a link. Looks malicious. Escalated.
```
No user, no timestamps, no evidence, no reasoning. L2 starts from zero.

**Good:**
```
Verdict: True Positive
Who:   m.alaa (Finance), mailbox m.alaa@corp.example
What:  Received "Overdue Invoice" email, clicked link, entered credentials
       on a fake Microsoft 365 login page
When:  Email 09:12 UTC, click 09:15 UTC, 2026-11-17
Where: Host FIN-PC-04 (10.10.20.14); hxxps://invoice-portal.example[.]com;
       sender billing@vendor-invoices.example[.]com
Why:   Lookalike domain + fake M365 page; user confirmed by phone he typed
       his password, so credentials are compromised
Next:  Password reset + session review needed. Escalated to L2
```

### Bad vs Good: Brute Force

**Bad:**
```
VPN brute force. Closed FP, probably forgot password.
```
"Probably" is not evidence. No counts, no source, no user confirmation.

**Good:**
```
Verdict: False Positive
Who:   VPN account s.hassan
What:  40 failed SSL VPN logins in 6 minutes, no successful login
When:  08:02–08:08 UTC, 2026-11-17
Where: FortiGate SSL VPN portal; source IP 198.51.100.23 (user's known home IP)
Why:   User changed password yesterday; phone mail client kept retrying
       the old cached password. User confirmed by phone; failures stopped
       after he updated the client. Known source, no success.
Next:  None. Closed at L1
```
[Extra] On Windows/AD, equivalent evidence is Event ID **4625** (failed logon) vs **4624** (success). Not from this room.

### Copy-paste template
The 5Ws come from the room. Actions/Next/Escalation lines are practical additions [Extra].

```
[Alert Report]
Alert / Severity:
Verdict: True Positive / False Positive
Who:   <user / account>
What:  <exact action or event sequence>
When:  <start – end, with timezone>
Where: <hostname / IP / URL / mailbox>
Why:   <evidence + reasoning for the verdict>
Actions taken: <logs reviewed / TI lookup / user confirmation>
Next steps needed: <password reset / isolation / none>
Escalation: <assigned to L2 name / not required>
```

## 4. Escalation

### When to escalate (4 conditions from the room)
1. Indicator of a **major cyberattack** needing deeper investigation or **DFIR**.
2. **Remediation** required: malware removal, host isolation, password reset.
3. **Communication** needed with customers, partners, management, or law enforcement.
4. You **don't fully understand the alert** and need senior help.

### SOC dashboard flow
```
1. Move alert to In Progress, do the analysis
2. Write the alert report, set verdict (e.g., True Positive)
3. If escalation is required, assign the alert to your L2 on shift
4. L2 gets a notification and starts from your report
```
Usually also **ping L2 in corporate chat or in person**. Some teams require a formal written escalation request with many fields. Follow your team's procedure.

### Asking L2 for help
- Fine, especially in your first months.
- **Discussing an alert you don't understand beats blindly closing it.**
- Bring what you've checked and specific questions.

### What L2 does after receiving the ticket
- Reads your report, contacts you with questions.
- Researches deeper and **validates it is indeed a True Positive**.
- Communicates with other departments if needed.
- For major incidents: starts a formal **Incident Response** process.

### Decision table

| Situation | Escalate? | Why |
|---|---|---|
| Confirmed FP (benign cause proven, e.g., cached password) | No | Close at L1 with a full report |
| TP + password reset / isolation / malware removal needed | Yes | Condition 2 |
| Ransomware / major attack indicators | Yes | Condition 1 |
| Customers, management, or law enforcement must be informed | Yes | Condition 3 |
| Analysis done, still don't understand the alert | Yes (L2 support) | Condition 4. Never blind-close |
| Authorized admin activity confirmed (e.g., sanctioned scan) | No | Handled at L1. [Extra] Some teams call this Benign True Positive. It is **not** an FP |
| SIEM logs unparsed / unsearchable | Report the issue | Investigate what you can, inform L2 on shift or SOC engineer |

**Don't mix the three:** reporting = documenting. Escalation = handing off for action. Communication = coordinating with people/departments.

## 5. Communication Cases (all 5 from the room)

| Scenario | What to do | Why |
|---|---|---|
| **L2 unavailable.** Urgent critical alert, no response for 30 min | Know where emergency contacts are. **Call L2, then L3, then your manager** | Critical alerts can't wait |
| **Slack/Teams account compromise.** Need to validate login with the user | **Never use the breached chat.** Use another method, e.g., **phone call** | Attacker may control or read that chat |
| **Alert flood.** Many alerts in a short time, some critical | Prioritise per the workflow **and inform L2 on shift** | Team must know the queue is abnormal |
| **Misclassified alert.** Days later you realize you likely missed a malicious action | **Immediately** contact L2 and explain your concerns | Threat actors can stay silent for **weeks** before impact |
| **Unparsed SIEM logs.** Can't finish triage | **Do not skip the alert.** Investigate what you can, report the issue to **L2 on shift or the SOC engineer** | Blind closure risks a missed breach |

[Extra] Ideally the team has written **Crisis Communication** procedures. Ask where they live on day one.

## 6. Key Terms

| Term | Meaning | Example |
|---|---|---|
| Alert report | Written documentation of your investigation with evidence | 5Ws comment in the ticket |
| Escalation | Passing the alert to L2 for deeper review/action | Assign TP to L2 on shift + ping |
| Communication | Coordinating with other departments during/after analysis | Ask IT if admin rights were granted; ask HR about a new hire |
| True Positive (TP) | Alert correctly flagged a real threat | Credentials entered on a phishing page |
| False Positive (FP) | Alert fired but no threat | Failed logins from an outdated cached password |
| [Extra] Benign True Positive | Real activity, rule worked, but authorized. Not an FP | Sanctioned vulnerability scan |
| L1 / L2 / L3 | Triage / deeper analysis and remediation / next senior contact in emergencies | Call L3 if L2 unreachable |
| DFIR | Digital Forensics and Incident Response | Pulled in for major attacks |
| Incident Response | Formal process L2 starts for major incidents | Coordinated breach containment |
| Crisis Communication | Team guides for critical unexpected situations | Emergency contact chain |
| [Extra] SLA | Agreed time limit to handle an alert by severity | Value set per team |
| In Progress status | Alert state showing you own it and are analyzing | First dashboard step |

## 7. Common Mistakes → Fixes

| Don't | Fix |
|---|---|
| Close a TP without escalating | TP + required action = assign to L2. A verdict alone remediates nothing |
| Comment "checked, looks fine" | Full 5Ws, especially **Why**. Logs expire in 3–12 months, your report is the permanent record |
| Blind-close an alert you don't understand | Request L2 support. Asking is expected |
| Verify a login via the compromised Slack/Teams chat | Phone call or another independent channel |
| Wait silently when L2 doesn't respond to a critical alert | Call L2, then L3, then manager |
| Skip an alert because logs are unparsed | Analyze what's available, report parsing issue to L2/SOC engineer |
| Hide a misclassification you notice days later | Tell L2 immediately |
| Call authorized activity an FP | FP = no threat. Real-but-authorized activity is handled at L1 ([Extra] often "Benign True Positive") |
| Escalate with no report | Report first, then assign. L2 should never restart from scratch |
| Contact other departments unnecessarily | Contact IT/HR only when you need facts for the analysis. L2 handles wider communication |

## 8. Practice: 3 Mini Scenarios

### Scenario A: Phishing with credential entry
*Finance user reports an "invoice" email. Logs show a click and a login from an unusual IP right after.*

```
Verdict: True Positive
Who:   r.nabil (Finance), r.nabil@corp.example
What:  Clicked invoice link, entered credentials on fake M365 page;
       afterwards a successful mailbox login from 203.0.113.66
When:  Click 10:04 UTC; suspicious login 10:07 UTC, 2026-11-17
Where: FIN-PC-02 (10.10.20.12); hxxps://billing-portal.example[.]com
Why:   Lookalike domain, fake login page, login from unfamiliar IP minutes
       after the click; user confirmed entering his password (phone call)
Next:  Password reset, session review, mailbox rule check
```
**Decision: Escalate.** Condition 2 (password reset) and possible mailbox compromise.

### Scenario B: VPN failed logins
*50 failed SSL VPN logins for one account, all from the user's known home IP, no success.*

```
Verdict: False Positive
Who:   s.hassan
What:  50 failed SSL VPN logins, zero successes
When:  07:55–08:03 UTC, 2026-11-17
Where: FortiGate SSL VPN; source 198.51.100.23 (user's known home IP)
Why:   Password rotated yesterday; VPN client retried the old cached
       password. User confirmed by phone; failures stopped after update.
       Known source, no success, no other accounts affected.
Next:  None
```
**Decision: No escalation.** Benign cause proven. Close at L1 with the report.

### Scenario C: Unfamiliar admin tool
*An admin account runs an unknown PowerShell tool on a server. You can't identify it and IT hasn't replied yet.*

```
Verdict: Not yet determined. Escalating for L2 support.
Who:   adm-khaled (admin account)
What:  Executed unrecognized PowerShell tooling on a server
When:  14:22 UTC, 2026-11-17
Where: SRV-APP-01 (10.10.40.21)
Why:   Tool not in known-admin baseline; IT confirmation pending;
       cannot rule out malicious use of valid admin credentials
Next:  L2 review while IT confirmation is requested

**Decision: Escalate (L2 support).** Condition 4. Never blind-close what you don't understand. Keep it In Progress with findings documented.

## 9. Quick Revision Notes
- Triage classifies. **Reporting documents, escalation acts, communication coordinates.**
- Funnel: most alerts end at L1 (FP or handled). Complex/threatening go to L2. L2 remediates most breaches. Major incidents go to formal IR/DFIR.
- 3 report purposes: context for L2, permanent record, sharpening your skills.
- Retention: raw SIEM logs **3–12 months**, alerts **indefinitely**.
- 5Ws: Who, What, When, Where, **Why (most important)**.
- Escalate if: major attack/DFIR, remediation needed, external communication needed, or you don't understand the alert.
- Dashboard flow: **In Progress → analyze → report + verdict → assign to L2 on shift** (+ ping in chat/person).
- L2 then: reads report, asks questions, researches, validates TP, contacts departments, starts formal IR if major.
- Asking L2 for help is normal, especially early on.
- L2 unreachable on a critical alert (30 min): **call L2, then L3, then manager**.
- Compromised Slack/Teams: verify by **phone**, never the breached chat.
- Alert flood: prioritise per workflow **and** inform L2 on shift.
- Misclassified days ago: tell L2 **immediately**. Attackers can be silent for weeks.
- Unparsed logs: don't skip. Analyze what you can, report to L2/SOC engineer.
- TP = real threat. FP = no threat. [Extra] Authorized-but-real activity ≠ FP.

## 11. SAL1 / SOC Simulator Tips
Only [Extra] practical advice. None of this is claimed as exam content.

- Use the report template on every alert. Never leave a comment empty or vague.
- Follow the dashboard order: **In Progress → analyze → report → verdict → escalate or close.** Don't set a verdict before checking surrounding events.
- Cite evidence in **Why**: "user confirmed by phone", "no successful login", never "looks fine".
- Match verdict to action. TP needing remediation → assign to L2. FP → close with proof of the benign cause.
- Uncertain alert: document what you checked and request L2 support. Don't blind-close.
- [Extra, unverified] If a scenario mentions a breached chat, unparsed logs, or an unreachable L2, apply the room's matching procedure (phone call / report to engineer / call chain).
- Memory anchors from the room: 3 purposes, 5Ws, 4 escalation conditions, 4-step dashboard flow, L2 → L3 → manager chain, 3–12 months vs indefinite retention.
- Your network background helps: for AD/VPN alerts, reason from 4624/4625 patterns and FortiGate logs. Write the report so a non-technical reader (manager, HR) can follow Who/What/Why.
